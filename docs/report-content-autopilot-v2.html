Kern-Wahrheit: Bausteine ja, Workflow nein. Heute könnte kein Kunde über das System auch nur einen einzigen Post erzeugen — der Produktkern (Kunde antwortet → Folgefrage → fertiger Post im Chat → Feedback) existiert in keiner Form (M18/M24/M25 alle rot), und der einzige vollständige reale Pipeline-Lauf (Setup mit Eric-Transkript) ist nachweislich gebrochen (#33).
Technologie-Urteil (kurz): Die Stack-Wahl (FastAPI · Celery · PostgreSQL+pgvector · React/Vite · Requesty-EU-LLM-Seam · Docker) ist für Produkt und Team-Größe überwiegend angemessen — bewusst betreibbar statt hip, nicht overengineered. Zwei Risiken sind klein im Code, groß in der Wirkung: (1) Tenant-Isolation rein applikativ ohne Postgres-RLS; (2) drei direkte US-LLM-Calls brechen die EU-Souveränität bei sensiblen Inhalten.

1 Vision — das Endbild

Ein KI-gestützter LinkedIn-Content-Autopilot für Agentur-Endkunden. Der Kunde sammelt laufend Rohmaterial, wird einmalig per Onboarding erfasst (Kontext/Voice/Avatar) und bekommt danach im Telegram-Chat über drei Eingangspfade Anstöße. Aus einer Sprachnachricht entsteht — gestützt auf seine echte Stimme, seine Werte und sein Avatar-Profil — ein fertiger Post zurück im Chat, mit Feedback-Schleife.

Der Workflow in einem Satz: Sammeln → einmaliges Setup (Kontext/Voice/Avatar) → kategorisierter Speicher → Anstoß über einen der drei Chat-Pfade → Sprachnachricht/Transkript (+ max. 2–3 Rückfragen) → P12 Post-Erstellung → P12b Optimierung mit Voice/Werte/Avatar → fertiger Post zurück im Telegram-Chat → Feedback-Loop. P17 lernt nebenbei mit.

Die fünf Bahnen des Figma-Boards (SOLL)

Bahn 1 · Briefing

„Alles kann Content werden." Content-Arten personal/Trust/Projekte. „Sammeln, Sammeln, Sammeln": Fotos, Ideen, YouTube → Rohmaterial-Strom.

Bahn 2 · Setup

Einmaliges Onboarding: Mini-Formular + 60-min-Gespräch (8 Phasen) → P01 Kontext · P02 Website · P03 Voice · P04 Avatar → DB. Voice-Fallback.

Bahn 3 · Speicher

Alles laden → kategorisieren (Werte/Stories/Konflikte). „Struktur, damit die KI das sinnvoll nutzen kann." LinkedIn-Erfolgsanalyse (später).

Bahn 4 · Input

Drei Pfade in den Chat: A — P07 Research-Push (Hooks) · B — P08 Fragenliste · C — P09 „gib mir Ideen". Eigene Idee → P13 (3 Aufhänger).

Bahn 5 · Output

Transkript → P12 (Voice+Werte+Avatar) → P12b → fertiger Post im Chat → Feedback-Loop (P16) + Kosten. P17 aktualisiert die Entitäten inkrementell.

Board-Notizen: „Alles findet in WhatsApp/Telegram statt" (Beta: Telegram-first) · „Claude Opus 4.6 als Modell für Content" (→ Entscheid #42) · „Wie viele Tokens sind nötig?" (Kosten-Transparenz).

3 Die fünf wichtigsten Erkenntnisse der visuellen Analyse

01Board-Trias = Voice/WERTE/Avatar

v2 führt Kontext/Voice/Avatar. „Kunden Werte" existiert nicht als Speicher; Werte-Chunks versanden für die Post-Erstellung. Größte unerkannte Architektur-Lücke — ohne sie ist auch #41 (P17) nicht vollständig umsetzbar. Konzept liegt vor (CONCEPT-43-werte-entitaet.md).

028 Gesprächsphasen sind nur 6

„Expertise & Fachwissen" fehlt komplett — fachlicher Substanzverlust fürs Setup. War unsichtbar, weil bisher nur die Existenz des Wizards geprüft wurde, nicht seine Phasen-Struktur.

03Kunden-ID korrekt, Provenienz fehlt

Die UUID-pro-Eintrag entspricht dem Board exakt, aber Transkript-/Formular-Link fehlen — das Transkript durchläuft die Pipeline und verschwindet ohne Quell-Verweis.

04P13 & Feedback sind Einmündungen

P13 ist visuell kein Endpunkt, sondern mündet in den Transkript-Knoten; der Feedback-Loop geht zum Transkript zurück (= neuer Durchlauf, nicht bloß „regenerieren"). Konsequenz für #36/#19/#37.

05Farb-Semantik bestätigt die Priorisierung

Alles Blaue (LinkedIn) und Graue (P05/P06) ist laut Board selbst optional/später — die ⏸-Entscheidungen sind keine Abweichung. Umgekehrt: alles Gelbe/Orange muss für „genau so" stehen — und davon fehlen Post-im-Chat, Intent-Routing, Werte-Entität, P02, Voice-Fallback, P17, 8 Phasen.

7 Wo ein Entwickler ansetzen sollte (Backend)

Priorisiert nach Wirkung. Jeder Punkt: Was / Wo / Warum / Hebel — belegt durch Code-Lektüre.

1

US-LLM-Bypässe schließen Compliance · höchste Wirkung

Wo: voice_drift_task.py:310-314 · md_converter.py:133 · sensitive_detector.py:408

Warum: Direkte anthropic.Anthropic() → US-api.anthropic.com, bricht die EU-Souveränität genau bei Drift-/Sensibilitäts-/Konvertierungsdaten. Hebel: Auf call_pipeline_llm (Bedrock-EU) umstellen — der Seam existiert, reine Umverkabelung. (#41/#46)

2

Tenant-Isolation härten größter stiller Leak-Schutz

Wo: dependencies.py + alle services/*.py mit tenant_id-Queries

Warum: Keine Postgres-RLS (0 CREATE POLICY) — Isolation hängt vollständig an manuellem WHERE tenant_id; ein vergessenes Predicate = Cross-Tenant-Leak. Hebel: RLS-Policies pro Tabelle + SET app.tenant_id als Session-GUC (Defense-in-Depth). (#52)

3

Pipeline-Idempotenz P01→P12c Geld + Stabilität

Wo: p01_task.py, p12_task.py (max_retries=2), pipeline_pump_task.py

Warum: Retries ohne Idempotenz-Guard + Pump-Polling können Stufen doppelt ausführen (doppelte Kosten/Inserts), kein sauberer Resume nach Teilausfall. Hebel: Status-Guard pro Stufe + acks_late=True + DB-Unique-Constraint auf (tenant, stage). (#18)

4

Test-Suite lokal lauffähig / Sync-Async-DB entwirren Iterationsgeschwindigkeit

Wo: tests/conftest.py, models/base.py (sync + async Doppel-Engine)

Warum: Auf bare-Py3.9-venv brechen DB-berührende Tests bei Collection; Doppel-Engine ist dauerhafte Komplexität. Hebel: conftest-Stub/SQLite-Fallback oder gepinnte requirements-dev.txt + make test in Docker; mittelfristig Sync-Pfad reduzieren.

5

Modell-Pinning der -latest-Aliasse Reproduzierbarkeit + Budget

Wo: provider_resolver.py, pipeline_llm.py (S2–S5 *-latest)

Warum: -latest = nicht reproduzierbare Evals + stilles Kosten-/Verhaltens-Drift (verursachte schon einen Overrun). Hebel: auf datierte Aliasse pinnen (S6 ist Vorbild), Bump nur mit Eval-Gate. (#30)

6

Observability über llm_call_log vereinheitlichen Audit-Belastbarkeit

Wo: llm_call_log.py, provider_resolver.track_cost, pipeline_llm.py

Warum: Cost-Tracking über zwei Seams verteilt → Lücken/Doppelzählung schwer auditierbar. Hebel: einheitliches Logging (correlation_id + tenant + tier + cache-tokens) an einer Stelle. (stützt #48/#51)

7Fail-open-Cap/Throttle bewerten

llm.py:303-328 fängt jede Exception → pass. Bei DB-Ausfall werden Budget- und Rate-Limits lautlos deaktiviert — genau wenn ein Runaway am teuersten ist. Hebel: Sentry-Alert bei Cap-Failure; Throttle ggf. „fail-closed".

8Pydantic-v2-Settings — Quick Win

config.py:71 nutzt v1-Style class Config statt model_config = SettingsConfigDict(...) — in pydantic-settings 2.7 deprecated. Hebel: Einzeiler-Migration, niedriges Risiko.

9 Experten-Bewertung der Technologie

Ist die zugrundeliegende Technologie passend? Bewertet pro Achse — begründet, nicht gefällig.

Web/API & Validierung
FastAPI + Pydantic v2
✓ Passend
Quasi-Default für LLM-Pipeline-SaaS, hier korrekt (async, DI für Tenant/DB, Pydantic-Settings). Vorbehalt: config.py:71 nutzt noch v1-Style class Config (Deprecation).
Async / Orchestrierung
Celery + Redis + Beat
~ Vorbehalt
Robust für periodische Jobs. Für die mehrstufige Kette P01→P12c nur „gut genug": keine echte Workflow-Engine, Verkettung über Pump-Polling + DB-Status statt Celery-Canvas; Idempotenz-Guards/acks_late fehlen. Temporal wäre Overkill → Celery behalten, Idempotenz nachrüsten.
Datenhaltung
PostgreSQL + pgvector
✓ Passend
Für diese Datenmengen die richtige Entscheidung — schlägt Pinecone/Weaviate für ein Ein-Mann-betreibbares Setup. HNSW korrekt. Risiko: keine RLS → Isolation rein applikativ.
LLM-Abstraktion
Requesty-Seam, Tier S1–S6
~ Vorbehalt (ernst)
Der pipeline_llm-Seam ist vorbildlich (IDs an einer Stelle, EU gepinnt, harter RuntimeError ohne Router). Aber drei Direct-Anthropic-US-Bypässe in Nebenpfaden. p08 ist sauber. Architektur tragfähig, Lecks isoliert behebbar — compliance-seitig scharf.
EU / DSGVO-Souveränität
Architektur-Constraint
~ Vorbehalt
Stack kann es tragen (Bedrock Frankfurt, Vertex EU, EU-Postgres). Leckstellen: (1) die drei US-Calls; (2) Telegram = US-Firma als Kern-Kanal (strukturell, nicht im Code lösbar); (3) PII-in-Logs nur heuristisch redigiert.
Frontend
React/Vite, 32 kLOC
~ Leicht überinvestiert
Richtige schlanke Wahl (kein Next.js-Overhead). Aber Funktionsbreite (Force-Graph-Memory-Viz, Carousel-PDF-Editor) ist für eine Telegram-first-Beta üppig — das Dashboard ist laut Vision nicht der Kundenpfad. Kein TypeScript bei 32 kLOC = wachsendes Wartungsrisiko.
MCP-Server
FastMCP, SSE
? Timing fragwürdig
Investition minimal (1 Datei, dünner Proxy) = günstige Optionalität. „MCP ist das Produkt" (Vision) vs. Telegram-first-Realität. Vertretbar weil so billig gebaut.
Gesamturteil.
