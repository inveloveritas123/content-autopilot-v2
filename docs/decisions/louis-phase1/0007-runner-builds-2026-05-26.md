# ADR 0007 — Technische Entscheidungen aus den P03/P04-Runner-Builds (2026-05-26)

**Datum:** 2026-05-26
**Status:** Akzeptiert
**Entschieden von:** Louis (mit Claude), validiert mit Eric
**Bezogen auf:** ADR 0003 (Sonnet als Default), ADR 0004 (TypeScript-Runner statt n8n)

## Kontext

Beim Bau der P03- und P04-Runner sind mehrere kleine, aber für das Verhalten der Pipeline relevante Entscheidungen entstanden — keine einzeln groß genug für ein eigenes ADR, aber zusammen wichtig genug, dass sie nicht nur als Code-Kommentare verstreut existieren sollten. Dieses ADR fasst sie zusammen, damit ein neuer Entwickler nicht raten muss, warum die Runner so aussehen, wie sie aussehen.

Alle fünf Entscheidungen sind bereits im Code umgesetzt — dieses ADR dokumentiert den Status Quo.

---

## 1. Streaming-API statt `messages.create` für alle Runner

**Entschieden:** Alle drei Runner ([run-p01.ts:128](../../scripts/run-p01.ts#L128), [run-p03.ts:127](../../scripts/run-p03.ts#L127), [run-p04.ts:140](../../scripts/run-p04.ts#L140)) nutzen `client.messages.stream({...}).finalMessage()` statt `client.messages.create({...})`.

**Warum:** Lange JSON-Outputs (besonders P03 mit Voice-Profil) provozieren `ETIMEDOUT`-Fehler bei der nicht-streamenden API, weil das Anthropic-SDK auf die komplette Antwort wartet bevor es Bytes zurückgibt. Streaming sendet kontinuierlich Bytes — die HTTP-Verbindung bleibt aktiv, kein Idle-Timeout. `finalMessage()` rekonstruiert am Ende das vollständige Response-Objekt, sodass der Aufruf-Code (Token-Usage, content-Blocks) identisch bleibt.

**Konsequenz:** Kein UX-Verlust (wir streamen ohnehin nicht an User), aber stabile Läufe auch bei 10k+ Output-Tokens. Eingebaut sind zusätzlich `timeout: 600_000` (10 Min) und `maxRetries: 2` als Sicherheitsnetz.

## 2. `max_tokens` pro Prompt unterschiedlich gesetzt

**Entschieden:**

| Prompt | max_tokens | Begründung |
|---|---|---|
| P01 | 8 192 | Strukturierte Extraktion mit klar begrenztem Schema. Output bisher unter ~5k Tokens. Reserve reicht. |
| P03 | 16 000 | Voice-Profil ist der inhaltsreichste Output (12 Top-Level-Blöcke, viele Array-Felder mit `minItems`). Wurde bei 12k im Testlauf abgeschnitten. |
| P04 | 12 000 | Mittlerer Output. Mehr als P01 (mehr abgeleitete Felder), weniger als P03 (keine Voice-Beispiele). |

**Warum:** Anthropic rechnet `max_tokens` als Hardlimit ab. Zu hoch = unnötig hohes Output-Cost-Risiko bei Modell-Drift. Zu niedrig = JSON wird mitten im Output abgeschnitten und Validation schlägt fehl. Die Werte sind empirisch kalibriert.

**Konsequenz:** Neue Runner sollen `max_tokens` analog setzen — je nach erwarteter Output-Größe, nicht pauschal hoch. Bei Schema-Wachstum den Wert ggf. anheben (Marker: gespeicherte `p0X.raw-*.txt`-Dateien deuten auf Abbruch hin).

## 3. Opus-Key-Normalisierung im P03-Runner

**Entschieden:** [run-p03.ts:158-168](../../scripts/run-p03.ts#L158-L168) normalisiert die Top-Level-JSON-Schlüssel der Modell-Antwort:

```ts
const TOP_LEVEL_ALIASES: Record<string, string> = {
  emotional_ausdruck: "emotionaler_ausdruck",
};
parsed = Object.fromEntries(
  Object.entries(parsed).map(([k, v]) => {
    if (k.startsWith("_")) return [k, v];
    const lower = k.toLowerCase();
    return [TOP_LEVEL_ALIASES[lower] ?? lower, v];
  }),
);
```

**Warum:** Opus 4.7 übernimmt vereinzelt die Überschriften-Schreibweise aus dem System-Prompt (z.B. `### GRUNDTON` → JSON-Key `"GRUNDTON"`). Außerdem fällt das deutsche „-ER"-Suffix in `emotionaler_ausdruck` manchmal weg → `emotional_ausdruck`. Schema-Schlüssel sind aber konsequent snake_case lowercase. Ohne Normalisierung würde die Validation an Schreibweisen scheitern, die inhaltlich korrekt sind.

**Begrenzt auf:** P03-Runner. P01 und P04 laufen mit Sonnet, der das Problem nicht zeigt. `_meta` bleibt unverändert (deshalb `if (k.startsWith("_"))`-Guard).

**Konsequenz:** Wenn weitere Top-Level-Keys auftauchen, die Opus mit Wackler schreibt → Eintrag in `TOP_LEVEL_ALIASES` ergänzen. Das ist kein Workaround für ein Schema-Problem — es ist ein bewusster Toleranzbereich für ein bekanntes Modell-Verhalten. Nested-Keys werden **nicht** normalisiert, weil dort bisher keine Wackler auftraten und tiefer Eingriff in die Datenstruktur das Schema unscharf machen würde.

## 4. Wortschatz-Lockerung im P03-Schema

**Entschieden:** In [schemas/p03.schema.json](../../schemas/p03.schema.json) sind drei Wortschatz-Felder bewusst tolerant gefasst:

- `signalwoerter` (Z. 88-105), `fuellwoerter` (Z. 106-122), `verbotene_woerter` (Z. 127-143): `oneOf: [string, object]` — entweder einfacher String, oder strukturiertes Objekt mit `{wort, haeufigkeit, kontext}` / `{wort, haeufigkeit, empfehlung}` / `{wort, grund}`.
- `fuellwoerter` (Z. 107) und `sprachbarrieren` (Z. 211) akzeptieren zusätzlich `["array", "string"]` als Top-Level-Typ — auch ein einzelner String als ganzes Feld ist erlaubt.

**Warum:** Modelle (besonders Opus) variieren zwischen zwei legitimen Darstellungen: kompakte Liste (`["weil", "dass", "also"]`) und strukturierte Liste (`[{"wort": "weil", "haeufigkeit": "hoch", "kontext": "..."}]`). Beide sind inhaltlich gleichwertig für Downstream-Konsum. Schema-Erzwingung einer Form würde willkürlich gute Outputs ablehnen.

**Konsequenz:** Konsumenten (P12, P12b) müssen beim Lesen prüfen, ob Element String oder Objekt ist — das ist explizit eingeplant. Das Voice-Profile-Merge-Layer ([ADR-0006](0006-kuratiertes-voice-profile.md)) reicht die Felder durch, ohne sie zu vereinheitlichen.

## 5. `avatar_basis` in P04 optional

**Entschieden:** In [schemas/p04.schema.json](../../schemas/p04.schema.json) Z. 7-17 ist `avatar_basis` **nicht** in `required`. Alle anderen Top-Level-Felder (`identitaet`, `innenwelt`, `wunschbild`, `content_trigger`, `sprache_der_zielgruppe`, `alltagsszenen`, `blockaden`, `ausloesemoment`) sind Pflicht.

**Warum:** `avatar_basis` (Felder `abgeleitet_von`, `zielkunde_kurzprofil`) ist eine Quellen-Doku — wo kommt der Avatar her, was war die Grundlage in P01. Inhaltlich redundant zu `_meta.p01_source` plus dem `p01.zielkunde.beschreibung`-Feld. Manche P04-Läufe füllen es, andere nicht — beides ist OK. Pflicht zu machen wäre Schein-Strenge: das Modell würde leere Platzhalter erzeugen, nur um Validation zu bestehen.

**Konsequenz:** Konsumenten müssen `avatar_basis` als optional behandeln. Aktuell ist kein nachgelagerter Prompt darauf angewiesen (siehe Feldnutzungsmatrix in ADR-0006). Falls das Feld in einem Lauf existiert, ist es nice-to-have für Audit, sonst aus P01 ableitbar.

## Konsequenzen (übergreifend)

**Positiv:**
- Pipeline ist stabil unter realen Bedingungen (lange Outputs, Modell-Wackler).
- Schema-Toleranz ist bewusst und dokumentiert — kein „silent looseness", das später beißt.
- Neue Runner haben klare Vorbilder: Streaming + kalibriertes `max_tokens` + Normalisierung wo nötig.

**Negativ:**
- Schema-Validierung ist an drei Stellen weicher als bei einem idealen, modell-unabhängigen Vertrag. Wenn wir später das Datenmodell in Postgres pressen (Phase 2), müssen wir entscheiden: gleiche Toleranz in der DB (z.B. JSONB) oder Normalisierung im Voice-Profile-Merger.
- Die Opus-Key-Normalisierung in P03 ist Modell-spezifisch. Bei Wechsel auf ein anderes Modell prüfen, ob das Mapping noch nötig oder neu kalibriert werden muss.

## Trigger für Re-Entscheidung

- Wenn Anthropic SDK ein zuverlässiges Non-Streaming-Verhalten für lange Outputs bringt → Streaming könnte optional werden (heute lohnt sich Refactor nicht).
- Wenn Modell-Wechsel (z.B. Opus 5) das Key-Casing-Problem nicht mehr zeigt → `TOP_LEVEL_ALIASES`-Mapping entfernen.
- Wenn `avatar_basis` doch von einem nachgelagerten Prompt benötigt wird → entweder Pflicht machen, oder im Voice-Profile-Merger ableiten.
- Wenn das Wortschatz-Format sich in der Praxis auf eine Variante eingependelt hat → Schema verengen.
